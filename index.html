Every piece of litter has a long afterlife

Common waste outlives us by centuries. Knowing what something is — and where it should go — is the first step to keeping it out of nature. Figures below are widely reported decomposition ranges from environmental agencies; treat them as general guidance, not measurements of any single item.

Plastic · 100–450 years

Bottles and bags fragment into microplastics that enter soil and waterways. They don't biodegrade — they break into smaller pieces that wildlife can ingest.

E-waste · highly hazardous

Batteries and electronics can leach lead, cadmium and mercury. Never handle damaged batteries with bare hands — use a designated e-waste collection point.

Glass · ~1 million years

Glass is inert but effectively permanent, and broken shards injure people and animals. The good news: glass is endlessly recyclable without quality loss.

Metal · 50–200 years

Cans rust and can leach metals into soil, but scrap metal is valuable — aluminium recycling saves up to ~95% of the energy of making it from ore.

Paper · 2–6 weeks

Paper breaks down fast, yet in landfill it produces methane as it rots without oxygen. Recycling or composting clean paper avoids that entirely.

Organic · days to months

Food scraps belong in compost, not landfill. Even natural litter like fruit peels can harm wildlife by attracting animals to roadsides.

How the backend works — data flow

    
Your photo never talks to Gemini directly from the browser. It goes through a secure backend function, so the API key is never exposed.

    

      
1 · App / WebsiteUser uploads photo, submits cleanup, signs in

      
2 · Cloud FunctionsSecure backend validates request & user

      
3 · Gemini AIClassifies waste, returns structured JSON

      
4 · Firestore + StorageSaves scan, cleanup, points & photos

    

    
Same flow for points: Admin approves in Firestore → a trigger function calculates points from reward_rules → updates the user and writes a point_transactions record. The browser can never award points itself.

  


  
API — Cloud Functions
These are the real functions in functions/index.js and functions/gemini.js (full code on the Source Code page). All are callable / trigger functions — there is no public unauthenticated REST endpoint.

  

    

      
CALLABLEscanGarbageAuth required

      
Receives a waste photo from the app, sends it to Gemini via the server-side key, validates the JSON, saves it to garbage_scans and returns the impact report. Scanning earns 0 points.

      

        
Request{ imageBase64: string, mimeType: "image/jpeg" }

        
Response{ scanId, category, confidence, environmentalRisk, soilEffects, waterEffects, wildlifeRisks, recycling, safeHandling, disposal }

      

      
Validation: sign-in required · image type checked · max 10 MB · category must be one of 8 allowed values · confidence clamped 0–100.

    

    

      
FIRESTORE TRIGGERawardPointsOnApprovalServer only

      
Fires automatically when a cleanup_records document changes to Approved. Reads reward_rules/current, calculates points, and updates everything in one batch. Idempotent — approving twice cannot pay twice.

      

        
TriggeronDocumentUpdated("cleanup_records/{cleanupId}") when verificationStatus → "Approved"

        
Writescleanup_records.awardedPoints
users.totalPoints += points
point_transactions (new record)

      

      
Formula: basePoints + (bags − 1) × perBagBonus — values come from Admin reward rules, never hard-coded in the client.

    

    

      
CALLABLEsetAdminClaimAdmin only

      
Grants or removes the admin custom claim that unlocks the Admin Dashboard and review actions. The function itself checks the caller is already an admin — ordinary users get permission-denied.

      

        
Request{ uid: string, makeAdmin: boolean }

        
Response{ ok: true }

      

    

    

      
INTERNALanalyseWasteImage() — functions/gemini.js

      
Server-only helper called by scanGarbage. Reads GEMINI_API_KEY from functions/.env, calls gemini-2.0-flash:generateContent, strips code fences, parses JSON and validates category / risk before anything is saved or shown.

      
If the key is missing, it throws GEMINI_API_KEY is not configured — the app then stays in demo mode instead of inventing a result.

Database — Firestore collections
Six collections, exactly as defined in the rules and indexes in the source pack. Fields marked server-only can never be written by the app in the browser.

  

    
users
userId · displayName · email
profileImage · totalPoints [server-only]
createdAt · role via custom claim
Read: owner or admin only. Create: totalPoints must start at 0.

    
garbage_scans
scanId · userId · imageUrl
wasteCategory · confidence
environmentalRisk · scanDate
Create/read: own scans only. Written by the scanGarbage function.

    
cleanup_records
cleanupId · userId · beforeImageUrl
afterImageUrl · location · wasteCategory
verificationStatus [admin/server-only]
awardedPoints [server-only] · submittedAt
Create: must start as Pending with 0 points.

    
rewards
rewardId · title · description
pointsRequired · availabilityStatus
Read: everyone. Write: admins only.

    
point_transactions
transactionId · userId · points
transactionType · referenceId · createdAt
Write: Cloud Functions only (client write = denied for everyone).

    
leaderboard
userId · weeklyPoints · rankingPeriod
Read: public. Write: server only. Indexed by period + weeklyPoints.

    
Firebase Storage — photos
users/{userId}/…  (own folder only)
Images only · under 10 MB per file
Enforced by storage.rules on every upload.

    
reward_rules + app_config
reward_rules/current { basePoints, perBagBonus }
app_config { feature switches, announcement }
Read: public. Write: admins only — this is what the Admin Control switches save to in production.

Backend security rules — in plain words

    

      
Points cannot be faked
Firestore rules block clients from writing totalPoints, verificationStatus and awardedPoints. Only the approval trigger function can change them.

      
Keys never leave the server
The Gemini key exists only in functions/.env. The Firebase web config in the browser is safe to ship — it is not a secret and rules still protect the data.

      
Uploads are checked twice
App checks type/size before upload; Storage rules check again server-side. Cleanup duplicate-photo hash check runs before a submission can be approved.

Firebase setup (Phase 2–3)
1. Open console.firebase.google.com and create a project.
2. Add a Web App and copy its config into public/js/config.js (template below).
3. Enable Authentication → Email/Password.
4. Create Firestore and Storage, then deploy firestore.rules and storage.rules.
5. Run firebase deploy to publish.

    
Gemini setup (Phase 4)
1. Get a key from Google AI Studio.
2. Put it ONLY in functions/.env as GEMINI_API_KEY — never in website code.
3. Deploy the functions folder.
4. The website sends photos to the function; the function calls Gemini, validates the JSON, saves to Firestore and replies.

    
Android app (Phase 8)
